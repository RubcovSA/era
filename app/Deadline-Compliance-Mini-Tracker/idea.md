
# Building a Client‑Side E‑Rate Data Tool with Vue.js

## Overview and Goal
We will build a **pure client-side web application** using **Vue.js** that consumes public E-rate/USAC data to address a chosen customer pain point. The app will run entirely in the browser (no server component), fetch data from USAC’s Open Data **Socrata API**, and use the browser’s **local storage** for caching and persistence. By doing everything client-side with Vue, we can create an interactive UI quickly and even host it as a static site. This aligns with the requirements: calling external public APIs from the browser is fine (we’ll use USAC’s APIs with CORS), we’ll avoid heavy file processing in-browser (no large PDF downloads or complex parsing), and we’ll target primarily desktop browsers (so we can design for larger screens).

**Chosen Problem & Solution Idea:** One major pain point for E-rate service providers is *finding and tracking new RFPs (Form 470s) efficiently*【9†L99-L107】【9†L111-L119】. Currently they manually search multiple sources and risk missing opportunities. Our solution is a **“Form 470 RFP Tracker”** – a Vue-based web app that lets a user (e.g. a vendor sales director) easily filter and browse open E-rate Form 470 requests. This tool will display current open competitive bidding information (from USAC’s open data) and allow searching by criteria like state, service category, or applicant type. The app will highlight new postings and show how long until each RFP’s 28-day window closes. This clearly maps to a real pain (missed RFPs) and would make users say “oh wow, I can catch opportunities I might have missed.” It’s a small web app with a straightforward UX (filter controls + results list) that can be explained in minutes, but provides **real value** by consolidating and monitoring RFP data.

## Data Access via USAC’s Open API (Browser Calls) 
We will query the **USAC Open Data** platform (which is powered by Socrata) directly from the browser using AJAX calls. Fortunately, Socrata’s API **supports Cross-Origin Resource Sharing (CORS)**, so modern browsers can fetch data from it without needing a proxy. In fact, “CORS is currently supported in modern Chrome, Firefox, Safari, and IE (10+)… you don’t need to do anything special – your web browser and our servers will automatically negotiate the cross-origin request”【4†L184-L193】. This means we can use Vue’s HTTP client (like Axios or `fetch`) to call the open data endpoints directly from our Vue components.

**API Endpoints & Filtering:** USAC provides datasets for Form 470 (competitive bidding) information. For example, the “E-Rate Form 470 Tool Data” dataset contains basic info for each Form 470 (including applicant, dates, etc.), and a related “Services Requested” dataset details the requested services. These datasets can be accessed via Socrata’s RESTful API (e.g. a GET request to a URL like `https://opendata.usac.org/resource/{datasetID}.json`). We will likely focus on the Form 470 basic info dataset as our primary source. To keep the app fast and avoid downloading huge data files, we will **query with filters** so that we only retrieve relevant records – for instance, we can request “only Form 470s from the current filing window that are still open, in the user’s target state(s) or service category”. The Socrata API allows adding query parameters (SoQL) to perform server-side filtering and limit results【4†L198-L206】. For example, we could use a `WHERE` clause on the dataset (e.g., `? $where=state='TX' AND posting_date > '2025-11-01'`) so that the browser only downloads the subset of data the user actually needs, rather than the entire dataset. This approach honors the guidance to avoid heavy in-browser data processing by leveraging the API’s capabilities (the heavy lifting is done server-side).

**Handling CORS and Rate Limits:** Since we are calling the API from the browser, we must ensure the API supports it (USAC’s does via CORS, as noted) and be mindful of rate limits. The user is okay with direct calls, acknowledging that some public APIs might hit throttling limits. Socrata **uses application tokens** to distinguish applications and grant higher request quotas【22†L172-L180】【22†L211-L219】. In practice, we can register for a free app token and include it in our requests (e.g. by setting an HTTP header `X-App-Token`) to virtually eliminate throttling concerns【22†L219-L227】. For a one-day prototype, we might get by without a token if usage is low, but it’s good practice to include one to avoid being lumped into the shared IP pool【22†L172-L180】. We will also design the app to be efficient with calls – for example, we can fetch data once and cache it (or use pagination if needed) rather than repeatedly polling massive datasets. 

*Aside:* In the unlikely event an API we need doesn’t support CORS, we would consider alternatives like JSONP or a lightweight proxy. However, since our primary data source is the USAC open data which explicitly supports CORS and JSONP【4†L172-L181】【4†L184-L193】, we can proceed with direct browser calls confidently.

## Building the Front-End App with Vue.js
We will use **Vue.js** (likely Vue 3 with the CLI or Vite for quick setup) to structure our front-end. Vue is well-suited for this task because it lets us build a dynamic UI with minimal code and it’s easy to fetch and display data reactively. The plan:

- **Project Setup:** Initialize a Vue project (using `vue create` or Vite). We’ll have a main App component and possibly a couple of child components (for example, a component for filter controls and another for the results table, or a combined single component for simplicity given the time constraint).

- **API Calls with Axios:** We will use Axios (a promise-based HTTP client) to fetch data from the API. Vue’s documentation recommends Axios for consuming APIs and shows how to integrate it in component lifecycle hooks【16†L107-L115】. In our App component, we can use the `mounted()` lifecycle hook to load data when the app starts. For instance, *“we’ll create a data property that will house our information, and we’ll retrieve the data and assign it using the mounted lifecycle hook”*【16†L125-L133】. Concretely, in `mounted()` we might call: 

  ```js
  axios.get('https://opendata.usac.org/resource/FORM470_ID.json?$where=...&$limit=...')  
       .then(response => { this.form470Data = response.data; })  
       .catch(error => { console.error(error); this.error = true; })  
       .finally(() => { this.loading = false; });
  ``` 

  This will retrieve the initial batch of Form 470 records (perhaps the most recent or all open ones) and store them in a reactive data property (e.g. `form470Data`). We’ll include basic error handling and a `loading` flag as shown in Vue’s examples (so we can show a “Loading…” spinner or an error message if needed)【18†L231-L239】【18†L249-L257】.

- **Reactive State and UI:** Vue’s reactivity will automatically update the display whenever our data changes. We’ll bind the fetched data to an HTML table or list in the template. Each row might show key fields like the applicant name, Form 470 number, posting date, service category, and days until closing (which we can calculate in JavaScript). The UI will also include **filter controls** – for example, a dropdown to select state, checkboxes or multiselect for service types (Category 1 vs Category 2 services), and a text search box for keywords (to match e.g. school district name or service description). These inputs will be bound with `v-model` to data properties like `selectedState` or `searchQuery`. When the user changes a filter, we have two options:
   - *Client-side filtering:* Load a larger set of data once, then use computed properties or methods to filter `form470Data` in memory based on the selected criteria. This avoids extra API calls after initial load, but requires that the initial data set is reasonably sized.
   - *API-side filtering:* Trigger a new Axios request whenever filters change, including the filter parameters in the query (e.g. if user selects “TX”, fetch `...json?$where=applicant_state='TX'`). This ensures we only load what’s needed for the filter but means multiple calls. Given the open data API and the desire to avoid huge downloads, we likely will **use API-side filtering** for things like state or service type, especially if the dataset is large. Vue makes it easy to watch for changes – we can use a watcher on filter data or method calls on change events to re-fetch filtered data. For example, if `selectedState` changes, call the API URL with a `WHERE state = selectedState`. This keeps performance good and still notifies the user if loading (we can reuse the loading indicator logic).

- **Desktop-Focused UX:** Since the target users will mainly use desktop, we can design a layout that takes advantage of the wider screen. For instance, filters can be in a sidebar or a header toolbar, and results in a table with many columns. We won’t prioritize mobile responsiveness (though using modern CSS frameworks or flexbox could make it reasonably responsive by default, if time permits). The key for UX is clarity: a service provider should be able to **filter down to relevant RFPs in a few clicks** and see important details at a glance. We will ensure the interface is not cluttered – perhaps showing a summary count (e.g. “Showing 25 open RFPs in Texas for Category 2”) and an intuitive way to scan the list. Even if the styling is basic due to time, we will aim for a clean arrangement of elements (this demonstrates “taste for UX, even if rough”). Potential small enhancements include highlighting RFPs that are *new since your last visit* or *nearing their closing date* with a different color – these little touches make the tool immediately useful to the user.

- **Vue Component Structure:** In a one-day build, we might keep things simple in a single component. However, we could separate the Filter UI and Results Table into separate components if it improves clarity. Vue’s component system would let us reuse parts if needed (for example, a child component for an RFP row or a date countdown badge). This isn’t strictly necessary but could show some thoughtful structure.

## Using Local Storage for Caching & Persistence 
To enhance performance and user experience, we will use **Web Storage (localStorage)** to save certain data on the client. As the Vue documentation notes, storing data in the browser can significantly improve performance by **avoiding unnecessary refetching** and even allow some offline capability【19†L106-L114】. We plan to leverage localStorage in a few ways:

- **Remembering User Preferences:** We can store the user’s last used filters (e.g. state selection, service type, etc.) in localStorage. This way, if the user closes the app or refreshes later, we can load those preferences on startup so they don’t have to re-select their typical filters each time. For example, we can save a JSON object like `{ lastState: "TX", lastServiceType: "Internet" }` to localStorage whenever the user changes a filter. Vue makes this easy: we can use a `watch` on our filter data properties to write to localStorage whenever they change【19†L139-L147】. Conversely, in the `mounted()` hook of our component, we will check localStorage for saved values and initialize our data from them【19†L139-L147】. This technique (initializing state from localStorage in mounted, and saving on watch) is illustrated in Vue’s cookbook: *“Focus on the mounted and watch parts. We use mounted to load the value from localStorage... and on change, immediately write it back”*【19†L139-L147】.

- **Caching API Results:** Depending on how large the data is, we might cache some of the fetched data in localStorage as well. For instance, if the user loads all open Form 470s for their state, we could store that list (as a JSON string) locally. Then, if they come back later, the app could quickly load the old data from local storage and display it while also fetching updates in the background. This provides a snappier experience – the user sees something instantly, and then the newest data will replace it once the AJAX call completes. This is a pattern sometimes used in SPAs to hide latency. However, we must be mindful of data size: **LocalStorage is best suited for smaller data** like settings or moderately sized JSON (it’s typically limited to a few MB per domain). Complex or very large datasets would be better stored in IndexedDB if needed【19†L116-L124】. In our case, Form 470 data for one state or one season is likely on the order of thousands of records, which (if a few MB or less) could be stored. If it turned out to be too large, we would stick to querying the API on each load (which is fine given our use of filters). Since the assignment emphasizes *“ideas that work well without needing to download large files”*, we will avoid caching anything extremely bulky. 

- **Marking Viewed/New Items:** Another neat use of local storage is to keep track of which RFPs the user has already seen. We could store identifiers of RFPs that have been viewed or the timestamp of the last check. Then, when the app loads new data, it can compare and highlight which entries are new since the last timestamp. For example, store `lastSeenTimestamp` or an array of `seenForm470IDs` in localStorage. This addresses the “tracking” aspect of the pain point – a user can quickly spot new opportunities they haven’t reviewed yet. This kind of data (IDs or a timestamp) is very small, perfect for localStorage.

Using localStorage in Vue is straightforward and doesn’t require additional libraries. We just use the Web Storage API directly (e.g. `localStorage.setItem('key', value)`). As noted, we handle it in Vue by reading on mount and writing on watch so that the UI state and storage stay in sync【19†L139-L147】. Overall, local storage will give our app a bit of statefulness across sessions and reduce redundant network calls, making it feel more polished without much extra code.

## Implementation Plan and Steps
Putting it all together, here’s how we’ll execute this in our ~1-day build:

1. **Setup Vue Project:** Use Vue CLI or Vite to scaffold a new app. This gives us a basic structure to start coding the interface. We’ll install Axios for HTTP requests. Optionally, if we want a quick UI boost, we might use a lightweight CSS framework (Bootstrap or Vuetify) for ready-made table styles and form controls; but given time constraints, plain HTML/CSS with some basic styling is acceptable.

2. **Design the Data Model:** Determine the fields we care about from the Form 470 dataset (e.g., Form 470 number, applicant name, applicant state, category of service, posting date, allowable contract date (which is posting date + 28 days), etc.). Knowing this, we can define our Vue component’s data properties. For example:
   - `form470List: []` – array to hold fetched RFP records.
   - `loading: true/false` – to track if data is being loaded.
   - `error: false` – to track if an API error occurred.
   - Filter model properties: `selectedState: ""`, `selectedServiceType: ""`, `searchText: ""`, etc., initialized either to defaults or from localStorage if available.
   - Maybe `lastUpdate: Date` to show when data was last refreshed (and store in localStorage for reference).

3. **Fetch Data in Mounted():** When the app loads, in `mounted()`, we do an initial fetch. If we have a saved filter state from localStorage, apply it. Then call the Socrata API for Form 470:
   - Construct the URL with appropriate query params. For example, if `selectedState` is not empty, include a `$where=applicant_state='XX'`. Also ensure we only get current data (maybe filter by Funding Year or by posting date in the last X months). We might also set a reasonable `$limit` if the API has one (Socrata defaults to 1000 records if not specified, which might be fine as a page size).
   - Include our **app token** in the header if we have one, to avoid any throttling issues【22†L219-L227】.
   - Await the response and then update `form470List` with the data. Turn off `loading`. If error, set `error=true` and perhaps show a message (e.g., “Unable to load data, please try again later.”).

4. **Display Data:** Use Vue’s templating to render the results. Possibly use a table: e.g.
   ```html
   <table v-if="form470List.length">
     <thead>...headers...</thead>
     <tbody>
       <tr v-for="item in filteredList" :key="item.form470_number">
         <td>{{ item.applicant_name }}</td>
         <td>{{ item.state }}</td>
         <td>{{ item.category_of_service }}</td>
         <td>{{ formatDate(item.post_date) }}</td>
         <td>{{ daysRemaining(item.post_date) }} days left</td>
         <td><a :href="item.form470_pdf_url" target="_blank">RFP Document</a></td>
       </tr>
     </tbody>
   </table>
   ```
   Here, `filteredList` could be a **computed property** that returns `form470List` filtered by the current `searchText` and maybe other criteria that are easy to do on the client (for example, a text search on applicant name). For filters that are simpler or already applied via API (like state), `form470List` might already be filtered from the query. If not, the computed property can filter by state too. Vue will automatically recompute and update the list whenever `form470List` or filter variables change.

5. **Filter Controls:** Add inputs bound with `v-model` for each filter. For instance, a dropdown for state (`<select v-model="selectedState">...state options...</select>`), and similar for service type. For text search, an `<input v-model="searchText" placeholder="Search by keyword...">`. We’ll add watchers on these filter variables to trigger data reload if needed:
   - If the dataset is large and we didn’t preload everything: on `selectedState` or `selectedServiceType` change, call a method `reloadData()` which fetches from the API with the new filter (this method can essentially repeat the Axios call with updated query params).
   - If we did load all and are just client-filtering: then no extra action needed; the computed `filteredList` will auto-update. In that case, we might still want to call the API periodically (like a refresh button or interval) to get new records, especially since new RFPs appear daily during the season. A “Refresh” button could fetch latest data on demand.

6. **Local Storage Integration:** In `mounted()`, after setting up data, we check localStorage:
   - If `localStorage.selectedState` exists, set `this.selectedState = localStorage.selectedState` (and same for other preferences). This loads the last used filters. Then we can call `reloadData()` using those filters.
   - In a `watch` section, watch each filter property. For example:
     ```js
     watch: {
       selectedState(newVal) { localStorage.selectedState = newVal; },
       selectedServiceType(newVal) { localStorage.selectedServiceType = newVal; }
     }
     ```
     This immediately saves any change. Similarly, if we decide to cache the data, after fetching we could do `localStorage.lastData = JSON.stringify(this.form470List)` (though careful with size). More likely, we just store a timestamp or small identifiers as mentioned (e.g., `localStorage.lastCheck = Date.now()` after a successful fetch, and maybe use that to highlight new vs old entries).
   - Because localStorage persists across sessions, the next time the user opens the app, their filters are pre-loaded and possibly we could indicate “Last updated 5 hours ago” using the saved timestamp, prompting them to hit refresh.

7. **Testing with Multiple Scenarios:** We will test the app with different data scenarios to ensure robustness (as per deliverable #5 in the prompt). For example:
   - Different states (ensure the filtering and API calls work for, say, CA vs NY – data might differ in volume).
   - Different funding years (if applicable – maybe ensure we are indeed pulling current year; older forms might be in data too but probably not needed).
   - Edge cases: no results (e.g. a filter combination that yields nothing, the app should handle “0 results” gracefully), a very large number of results (ensure the UI can handle it or maybe enforce a limit/paging), and weird data (e.g. applicant names with special characters, etc., though that’s more of a data quality issue).
   - We’ll also verify that localStorage persistence works by changing filters, refreshing the page, and seeing if the state is retained as expected.

8. **Polish & UX Considerations:** With remaining time, add small enhancements that make the tool delightful:
   - Highlight **new RFPs**: e.g., those posted in the last 48 hours could have a “NEW” label.
   - **Sort** functionality: maybe allow sorting the table by date or name. This could be as simple as clicking a header to reorder the `form470List` array (Vue will update the DOM accordingly).
   - **Link to details**: Provide a link to the actual Form 470 detail or the PDF of the RFP if available (the open data might include a URL or reference to the EPC download tool for the form PDF【10†L1-L8】). This way, users can click through to see full details or download the RFP document.
   - **Visual touches**: perhaps color-code rows by category (e.g., Category 1 vs Category 2 services) or by urgency (if <7 days left, highlight in red, etc.), to help users prioritize at a glance.

Throughout development, we’ll use AI assistance as needed for quick syntax help or troubleshooting, but we’ll make conscious decisions on what to simplify or skip given the time limit (e.g., if truly pressed, we might hardcode a smaller scope like focusing only on one state’s data to demonstrate the concept, but ideally we keep it flexible).

## Conclusion
In summary, this approach uses **Vue.js on the front end** to deliver an interactive, desktop-oriented tool that solves a real E-rate data problem without any server setup. We leverage **public open APIs** for data – specifically USAC’s Socrata APIs – which we can call directly from the browser thanks to CORS support【4†L184-L193】. By using API query parameters and not pulling more data than necessary, we respect the need to avoid heavy downloads or processing in the client. Vue’s reactivity and Axios make it straightforward to fetch and display the data in real-time, as documented in many examples【16†L107-L115】【16†L125-L133】. We also improve performance and user experience through **localStorage caching**, storing small bits of state (user filters, last seen items) locally to reduce repeated fetches and provide continuity between sessions【19†L106-L114】【19†L139-L147】. 

This all-client solution should be relatively quick to build and deploy. We end up with a **lightweight web app** (just static HTML/JS/CSS) that can be opened in a browser and immediately used by an E-rate stakeholder to find actionable data. Despite being built in ~one day, it will demonstrate our ability to understand the customer’s pain, utilize public data in a clever way, and deliver a “cool” tool with thoughtful UX touches. And because it’s all client-side, the barrier to try it out is low – just open a page – which is great for demoing our work in the follow-up. 

Overall, this plan meets all the requirements: it’s a novel solution (not duplicating an existing feature) that uses E-rate open data in a meaningful way, shows judgment in choosing a solvable problem within the time, and leverages modern web tech (and a bit of AI help) to build something that can provide real value quickly.
